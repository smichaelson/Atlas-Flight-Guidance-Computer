# BNO085 Sensor Hub

## Major firmware functions

| Function | Contract |
|---|---|
| `AtlasBno085_Init()` | Releases hardware reset, opens the official CEVA SH-2 stack, installs callbacks, and requires at least one product-ID entry. |
| `AtlasBno085_EnableReport()` / `DisableReport()` | Changes one SH-2 feature report with explicit microsecond interval and batch latency. |
| `AtlasBno085_Service()` | Drains no more than eight pending SHTP transfers per foreground call, dispatches decoded values, and returns a typed failure if servicing adds an I/O, protocol, decode, or asynchronous-reset fault. |
| `AtlasBno085_OnInterrupt()` | Records the active-low interrupt in constant-time ISR context; it performs no I2C transaction. |
| `AtlasBoard_GetBno085Sample()` | Copies the latest decoded value by SH-2 sensor ID and optionally consumes its availability bit. |

Source: [`atlas_bno085.h`](../../App/Inc/atlas_bno085.h), [`atlas_bno085.c`](../../App/Src/atlas_bno085.c), and the provenance-controlled [CEVA SH-2 library](../../ThirdParty/CEVA/sh2/README.md).

## Validation state

The Atlas adapter and official CEVA sources target-build without warnings. No BNO085 SHTP transcript has yet been captured from the physical board; report rates, reset timing, orientation, accuracy state, and reset recovery are bench-pending.

## RTOS access

The active-low EXTI callback only marks work pending. `AtlasIO` services at most eight SHTP reads per cycle and consumes the latest accelerometer, calibrated gyroscope, calibrated magnetic field, and rotation-vector reports into four named snapshot fields. Check the corresponding `ATLAS_RTOS_VALID_BNO_*` bit, use the matching `bno_*_received_at_ms` field for MCU-clock sample age, and separately inspect the SH-2 timestamp and accuracy for report quality. An asynchronous hub reset latches board service failure because volatile feature reports were lost; application code cannot clear that failure by reading the driver directly.

## Board contract

| Item | Atlas value |
|---|---|
| Fitted part | BNO085, U12 |
| Bus | I2C1, up to 400 kHz |
| 7-bit address | `0x4B` (HAL address `0x96`) |
| Reset | PB13 `BNO085_NRST`, active low |
| Host interrupt | PG0 `BNO085_H_INTN`, active low / EXTI0 |
| Timebase | Free-running TIM2 at 1 MHz, shared with GNSS PPS capture |
| Boot bound | Interrupt must assert within 4,000 ms after reset release |
| I2C retry policy | Three attempts, 25 ms HAL timeout each, 1 ms between attempts |
| Foreground bound | At most eight SHTP reads per `AtlasBno085_Service()` call |

The CEVA SH-2 implementation is process-global/singleton. Atlas supports exactly one BNO085 instance.

## Startup and transport behavior

1. Start the 1 MHz timer.
2. Assert reset for 10 ms, release it, and wait for active-low H_INTN.
3. Open CEVA SH-2 with the Atlas HAL adapter.
4. Register asynchronous-reset and sensor-event callbacks.
5. Request SH-2 product IDs and require a nonzero entry count.
6. At board level, enable these volatile reports:

| SH-2 report | Interval | Nominal rate |
|---|---:|---:|
| Accelerometer | 10,000 us | 100 Hz |
| Calibrated gyroscope | 10,000 us | 100 Hz |
| Calibrated magnetic field | 20,000 us | 50 Hz |
| Rotation vector | 10,000 us | 100 Hz |

SHTP-over-I2C length discovery deliberately performs a four-byte header read followed by a complete-frame read, because each BNO I2C read starts again at the SHTP header. The high continuation bit is removed before bounds checking. Frames larger than CEVA's supplied buffer are rejected; no heap allocation occurs.

## Data contract

CEVA decodes each report into `sh2_SensorValue_t`:

- calibrated acceleration is in m/s^2;
- calibrated angular rate is in rad/s;
- calibrated magnetic field is in microtesla;
- rotation vector components are `i`, `j`, `k`, `real`, with accuracy in radians;
- `timestamp` is the SH-2 event timestamp in microseconds;
- `status` low bits report the SH-2 accuracy class from unreliable through high.

The board keeps one latest-value slot per sensor ID. A new report overwrites the previous slot and sets the corresponding availability bit. This is an intentional latest-value mailbox, not a lossless log.

```c
sh2_SensorValue_t value;

if (AtlasBoard_GetBno085Sample(&atlas_board,
                               SH2_ROTATION_VECTOR,
                               &value,
                               true))
{
    /* Check value.status, age, quaternion norm, and the verified frame transform. */
}
```

## Health and fault interpretation

| Counter | Meaning |
|---|---|
| `interrupts` | H_INTN edges observed by EXTI. |
| `transfers_read` / `transfers_written` | Complete successful SHTP transfers. |
| `io_errors` | Repeated I2C transaction failure. |
| `protocol_errors` | Invalid SHTP length/header relationship. |
| `decoded_samples` / `decode_errors` | CEVA decode outcomes. |
| `async_resets` | SH-2 reported an unexpected hub reset. Feature reports must then be treated as suspect until recovered. |

At board level, the first non-OK service result is latched in `runtime_fault`. The RTOS supervisor then withholds the independent watchdog refresh so an unexpected hub reset or newly detected transport/protocol failure cannot silently leave the system running on stale fused data.

## Bench acceptance

1. Verify PB13 reset width and PG0 active-low boot assertion.
2. Capture the header-read/full-read I2C pattern and confirm address `0x4B` with no frame truncation.
3. Record every product-ID entry, software part/build/version, and reset cause.
4. Capture feature commands and at least 1,000 reports of each default type; verify rate, sequence continuity, units, and accuracy flags.
5. Slowly rotate the board through known orientations; verify quaternion norm/continuity and establish the sensor-to-body convention without guessing Euler order.
6. Force a hub reset and confirm `async_resets` changes, stale data is rejected by higher layers, and reports are deliberately re-established before use.
7. Hold H_INTN inactive and low in separate tests; confirm bounded boot failure and bounded foreground work/no interrupt storm.

## Known limits

- Default report setup is volatile and has no persistent dynamic-calibration policy.
- Hot recovery and automatic report re-enabling after an asynchronous SH-2 reset are not implemented. The current deliberate recovery is a whole-controller watchdog reset and complete board initialization.
- Latest-value storage can hide missed sequences unless the consumer checks sequence/timing.
- No board/body transform, calibration acceptance, sensor redundancy voter, or stale-data supervisor exists.
- The fused output must not be treated as independent evidence from the direct IMU/magnetometer without understanding shared physical error sources.
